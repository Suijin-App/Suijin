# MercuryDiff — wave 1 report

Status: done. `swift test --package-path Packages/MercuryDiff` passes 23 tests (two snapshot tests are opt-in).
A clean build including tests produces zero warnings under Swift 6 / complete concurrency. Screenshots were reviewed.

## Spike: TextKit 2 vs STTextView

Setup: a 5,100-line document in a 900×700 offscreen window. "Load" is setting the text plus the first display.
"Scroll" is 40 scroll steps through the document, each step forcing layout and display.

| View (release build) | Load | Scroll step avg | p95 | max |
|---|---|---|---|---|
| `NSTextView` (TextKit 2) | 8.4 ms | 2.1 ms | 2.5 ms | 2.9 ms |
| STTextView 2.4.1 (line numbers on) | 19.5 ms | 16.2 ms | 17.7 ms | 18.7 ms |

The full `DiffTextView` (gutter, custom fragments, 5,000 diff lines, debug build) measures 6–9 ms for load and
2.2 ms per scroll step. The numbers are printed by the `largeDiffLaysOutOnlyTheViewport` test.

**Decision: plain TextKit 2 `NSTextView`.** It is faster here, adds no dependency, and STTextView's
single-column ruler would not serve the two-column old/new gutter anyway. The STTextView spike lived only in
the scratchpad; nothing was added to the repo.

## What was built (`Packages/MercuryDiff/**` only)

- `DiffLayout.swift` builds one row per displayed line (hunk header, context, added, deleted, no-newline
  marker). Each row has its old/new line numbers and its range in the document text. The layout also
  reconstructs the old-side and new-side texts, and `documentSpans(oldSide:newSide:)` maps highlight spans
  from those texts back to diff rows. Context and added rows take new-side colors; deleted rows take old-side
  colors. Building 5,000 lines is well under the 500 ms test budget.
- `DiffTextView.swift` is a TextKit 2 `NSTextView` inside an `NSScrollView`:
  - Read-only and selectable, with the find bar enabled. The font is the AppKit counterpart of `MercuryFont.mono`.
  - Lines soft-wrap with a hanging indent. This keeps backgrounds full-width without huge layout fragments,
    and avoids horizontal scrolling in narrow panes.
  - Full-width row backgrounds come from a custom `NSTextLayoutFragment`, because TextKit 2 has no
    paragraph-level background attribute.
  - Highlight colors are applied as rendering attributes, so no relayout is needed. Visible spans go first;
    the rest follow in batches of 2,000 (about 5 ms each) with yields between them. Changing the diff cancels
    the running pass and clears the old colors.
- `DiffGutterView.swift` is an `NSRulerView` subclass. AppKit provides the gutter tiling and scroll tracking;
  only the marks are custom (old number, new number, +/− sign), drawn from the viewport's layout fragments.
  Changed rows get a stronger tint in the gutter.
- `DiffTheme.swift` derives dynamic colors from MercuryUI tokens: `ok`/`error` at low per-appearance opacity,
  `codeBackground`, `hairline`, `okText`/`errorText`. Token colors are system colors.
- `SyntaxHighlighter.swift` provides:
  - `language(forPath:)` and `@concurrent highlight(_:language:)`.
  - A cached query per language, and flattening into sorted, non-overlapping spans: inner captures win, and
    for identical ranges the grammar's convention decides (first pattern for official tree-sitter grammars,
    last pattern for the nvim-style Swift and Markdown grammars).
  - A `TokenKind` enum, which the contract referenced but did not define.
- `DiffDocumentView.swift` matches the contract (`NSViewRepresentable`, `init(diff:language:)`). It hosts
  `DiffTextView`, or a system `ContentUnavailableView` for binary files and for diffs with no hunks
  (mode-only changes or pure renames).
- UI strings live in `Resources/Localizable.xcstrings` via `String(localized:bundle:.module)`.

## Grammars (exact pins)

SwiftTreeSitter 0.25.0 (resolves tree-sitter 0.25.10). All nine languages build and pass a highlight test:

| Language id | Package @ version |
|---|---|
| swift | alex-pinkus/tree-sitter-swift 0.7.4-with-generated-files |
| javascript | tree-sitter-javascript 0.25.0 |
| typescript, tsx | tree-sitter-typescript 0.23.2 |
| python | tree-sitter-python 0.25.0 |
| json | tree-sitter-json 0.24.8 |
| go | tree-sitter-go 0.25.0 |
| rust | tree-sitter-rust 0.24.2 |
| markdown | tree-sitter-markdown 0.5.4 (block grammar only; inline markup is not highlighted) |

None were dropped. Two packaging workarounds were needed:

1. **Missing external scanners.** The tree-sitter-javascript and tree-sitter-python manifests check for
   `src/scanner.c` with `FileManager.fileExists` relative to the working directory, which SwiftPM does not
   set to the package root. The scanners are silently left out and the link fails; upstream master has the
   same bug. The fix is a small C target, `TreeSitterScanners`, holding the two unmodified `scanner.c` files
   (about 26 KB) from the same pinned tags. The Python one gets a pragma to silence an upstream
   64-to-32-bit conversion warning. Delete this target once upstream fixes its manifests.
2. **Vendored queries.** Highlight queries are copied into `Resources/Queries/highlights-*.scm`, each with a
   provenance header. SwiftTreeSitter's bundle lookup depends on main-bundle or test-bundle layout, and
   TypeScript/TSX need JavaScript's queries appended, as upstream's `tree-sitter.json` specifies.

Highlight timing for one 5,000-line side: about 85 ms in release and 350 ms in debug, plus a one-time query
compile. All of it runs off the main thread.

## Unresolved / for the controller

- Contract addition: `TokenKind` (public enum) is defined here. Also public: `DiffLayout`,
  `DiffDocumentContainerView`, `SyntaxHighlighter.supportedLanguages`, and `DiffTextView.setDiff(_:language:)`.
- `language(forPath:)` returns nil for extensions without a bundled grammar. Callers can pass the result
  straight to `DiffDocumentView`.
- Tokens can be wrong across hunk gaps, because elided lines are missing from the reconstructed sides
  (for example, a comment that opens outside the hunk). This is inherent to highlighting partial files.

## Follow-up: blank text column in on-screen windows (fixed)

**Symptom.** In the app the gutter rendered, but the text column was blank: no text and no row tints.

**Reproduction.** A scratchpad app in a real on-screen window, with the app's exact structure:
`NavigationSplitView` detail, then `HSplitView`, then a `DiffDocumentView` created after an async delay.
Captured with `screencapture -l`. Bisecting showed the problem was neither the zero initial frame nor SwiftUI;
hiding the ruler made the text appear.

**Root cause.** `NSView.clipsToBounds` defaults to false since macOS 14. AppKit hands the vertical ruler a
dirty rect wider than its bounds, because on this macOS the ruler floats over a full-width clip view.
`DiffGutterView.draw(_:)` filled that whole rect with the opaque code background, covering the text view.
Per-view offscreen captures never composite overlapping siblings, so the earlier snapshots could not show it.

**Fix** (in `DiffGutterView.swift` only; the app call site is unchanged):

- `clipsToBounds = true`
- `draw(_:)` intersects the dirty rect with its bounds before filling.

**Regression test.** `gutterNeverPaintsOutsideItsBounds` draws the gutter with a dirty rect three times its
width and checks that pixels outside its bounds stay transparent.

**Verification.** On-screen captures in light and dark are in `diff-screens/onscreen/`.

**Lesson for future UI checks.** Verify in a real on-screen window. Offscreen per-view captures cannot show
one view painting over another.
