## What was built

- **Broker in the PTY host** (`Packages/MercuryPTYProtocol/Sources/MercuryPTYHostKit/Orchestration/`):
  - `Broker`, `CallerIdentity` (stores only the SHA-256 of each token), `DispatchStore`, `TurnTracker`,
    `MessageDelivery`, `Escalation`, `BrokerTransport` (socket and spool), and `OrchestrationHub`, which keeps one
    broker per data root and serves the XPC endpoint.
  - `SessionManager` reports spawns, exits and client input to an observer. Its `injectInput` writes text that is not
    counted as user typing.
- **Transport.** Each request is one line of JSON over `<dataRoot>/orchestration/broker.sock`.
  - The socket is 600 inside a 700 directory, and a peer whose user ID differs is dropped.
  - A data root whose path is too long for `sun_path` gets its socket in the user's temporary directory instead.
  - There is also a file spool in the user's temporary directory. Codex's default `workspace-write` sandbox blocks
    Unix sockets but allows writes to `$TMPDIR` (verified), so the CLI falls back to the spool automatically.
- **Protocol 3** adds `orchestrationEndpoint(dataRoot:)`, which returns an anonymous XPC endpoint for
  `OrchestrationHostXPC` and `OrchestrationClientXPC`.
  - The endpoint carries the same code-signing requirement as the helper's Mach service.
  - A new helper answers an older app with the app's own version.
  - The Mach service name can be overridden with `MERCURY_PTYHOST_SERVICE` (only `com.tekmium.mercury.ptyhost.*`
    names). This is how tests run a private helper instance.
- **Backward compatibility (the scope you added).**
  - `PTYHostClient` (`Packages/MercuryTerminal`) accepts any helper from protocol 2 up to its own, records
    `hostProtocolVersion`, and asks the helper to exit only when the versions are truly incompatible.
  - `HelperVersionCheck` also treats an older protocol as stale, but still replaces the helper only when it is idle.
  - Orchestration shows as unavailable with a clear reason ("The running terminal host (protocol 2) predates
    orchestration…") and keeps retrying until the helper has been replaced.
  - Tests: `PTYHostClientNegotiationTests` (fake helpers at v2, v3, v1 and v4) and broker-side negotiation tests.
- **CLI.** The logic is `MercuryCLIKit`, with a thin `Tools/MercuryCLI/main.swift`. It is embedded at
  `Contents/Helpers/mercury` (`PRODUCT_MODULE_NAME: MercuryCLI`, your change, kept).
  - Commands: `worker start|list`, `send`, `ask`, `reply`, `done`, `inbox`, `whoami`, `skills get orchestration`,
    plus the hidden `hook claude` and `hook codex-notify`.
  - Every command takes `--json`, which prints sorted keys in the shape `{ok, result, text, error{code,message,hint}}`.
  - It accepts Orca spellings (`worker-start`, `worker_done`, `--question`, `--outcome`), reads `@file` and `-`
    (stdin), and suggests the closest command or flag on a typo.
  - Exit codes: 0 done, 1 refused, 2 usage error, 3 not a Mercury terminal, 4 Mercury unreachable.
- **Launch** (`SessionRuntime.makeLaunch` only).
  - Every session gets `MERCURY_SESSION_TOKEN` (environment only, never in arguments), the socket and spool paths,
    and `MERCURY_CLI`. The CLI folder goes first on `PATH` for agents and shells.
  - Claude: `--plugin-dir <dataRoot>/orchestration/claude-plugin` (the skill).
  - Codex: `-c notify=[mercury, hook, codex-notify, --, <the user's own notify…>]`.
  - Codex workers: `-c projects={"<realpath of repo>"={trust_level="trusted"}}` for that launch only (see decisions).
- **Worker start in the app** (`App/Features/Orchestration/WorkerLauncher.swift`).
  - It uses the coordinator's folder or a new worktree, named after `--name`, with a suffix when the name is taken.
  - The new worktree branches from what the coordinator has checked out.
  - `--account` matches an account by ID prefix, label or email.
  - The user's selection and tab are restored afterwards, and a start failure goes to the coordinator instead of an
    alert.
- **Delivery.**
  - A message is typed only after an agent signal says the turn ended: Claude's `Stop` or `Notification(idle_prompt)`
    hook, or Codex's `notify`. A permission prompt blocks delivery.
  - Delivery waits while the user typed in the last 3 s.
  - Messages waiting together go in one bracketed paste, followed by Return after a separate delay. A Claude session
    that shows no `UserPromptSubmit` within 6 s gets one more Return.
  - Each message is marked delivered before it is typed, so it is never typed twice.
  - A Return from the user while the agent is idle counts as busy until a turn signal arrives, or until 20 s pass with
    no output.
- **Escalation.**
  - A worker that ends its turn without `ask` or `done` is escalated after a 5 s grace period, so a report still on its
    way is not mistaken for a stall.
  - A worker whose process exits without `done` is escalated at once, with the exit code or signal.
  - A failed start is escalated (or returned directly to the caller if it is still waiting).
  - A message sent to a finished worker becomes a follow-up Task with new Task and Dispatch IDs.
- **UI.**
  - `WorkerTreeView` shows worker rows under the coordinator's row in your flat sidebar: plain rows with a status glyph
    that pulses while the worker asks or is stalled.
  - `OrchestrationInspectorSection` shows the spec, status, dispatch ID, summary and messages.
  - `OrchestrationSettingsSection` shows the broker status and the opt-in `~/.claude/skills` toggle (off by default).
  - A notification is posted when a coordinator waits on a permission prompt, or ends its turn with a worker's question
    unanswered.
- **Skill:** `App/Resources/Skills/mercury-orchestration/SKILL.md`, a folder resource. Phase 6 now has a
  **Verified** section with the Codex 0.166.0 findings.

## Decisions and deviations

- **Broker state lives in the helper's own JSON file,** not in the app database (as you asked). The `v4_orchestration`
  migration stays an empty placeholder whose comment says why. The shared models are in MercuryPTYProtocol, so there
  is no MercuryCore `Orchestration/` folder.
- **Broker code is in MercuryPTYHostKit,** not `Helpers/…/Orchestration`, so package tests can cover it.
  `Helpers/MercuryPTYHost/main.swift` only wires it up.
- **Codex `notify` is a per-launch `-c` override,** not written to `config.toml`. This covers the user's own login
  too, avoids the config mirror rewriting it, and chains the user's existing notify program.
- **Skills.** A managed Claude profile's `skills` folder is a symlink to the user's `~/.claude/skills`, so writing
  there would change the user's folder. Instead Claude loads the guide with `--plugin-dir` (verified). For Codex, the
  guide is copied only into managed homes whose `skills` folder is their own; homes linked to `~/.codex/skills` get
  the guide from the worker prompt and from `mercury skills get`.
- **Claude settings allow `Bash(mercury:*)`.** A worker reports from a terminal nobody watches, where a permission
  prompt would stall the whole orchestration.
- **Codex workers pre-trust their folder for that launch only.** Codex's trust screen cannot be answered in a
  worker's terminal, and answering it would save the folder in `~/.codex/config.toml`. Codex keys trust by the real
  path (`/private/var/…`, not `/var/…`).
- **Test-only `MERCURY_PTYHOST_SERVICE` override,** so end-to-end tests never share the user's helper. The runner
  script is in the scratchpad (`run-orch-e2e.sh`).
