## Key design decisions

- **Spawn in C, not Swift.** Code between `fork` and `exec` must be async-signal-safe, so a small C shim does
  `posix_openpt` → `fork` → `setsid` → `ioctl(TIOCSCTTY)` → `dup2` → close all fds ≥ 3 → reset signal mask and
  dispositions → `chdir` → `execve`. A close-on-exec status pipe reports chdir/exec failures as thrown errors (the
  failed child is reaped). The parent keeps the slave open until exit so output written just before the child exits
  is not lost. The environment is exactly the request's (matches `TerminalLaunch`: "nothing is inherited").
- **No gap and no duplicate on attach.** Every byte goes into the scrollback first and gets an absolute stream offset.
  On the session's serial queue, attach takes the snapshot, sends the XPC reply, and registers the attachment at
  `totalWritten`, all in one step. Live output is then served from the scrollback by offset, so the reply always
  precedes the stream on the connection. On the client, the engine discards bytes that arrive before the reply
  (stale data from a previous attachment), buffers bytes between the reply and the caller resuming, and appends
  them to the returned scrollback. The proof is `attachDuringHeavyOutputHasNoGapOrDuplicate`: it attaches while
  `seq` is writing about 2.2 MB, and scrollback plus stream equals the host scrollback byte for byte.
- **Backpressure.** Each attachment has a 1 MB in-flight window that is released by
  `NSXPCConnection.scheduleSendBarrierBlock`. A slow client is fed later from the ring. If it falls behind the ring,
  it skips to the oldest byte still held. The read loop never waits on XPC.
- **Batching uses a token bucket.** Up to 4 flushes go out immediately, then at most one per 8 ms, or immediately
  once 64 KB is pending. Two measurements drove this. Plain 8 ms batching delayed keystroke echo by ~8 ms. Flushing
  whenever the transport was idle cut latency to 0.04 ms but sent 7–9k messages for 2.2 MB. The bucket keeps typing
  echo below 1 ms while bulk output still goes in about 55 messages.
- **Exit detection.** A process `DispatchSource` handles exit, plus a check in the registration handler and a sparse
  backoff `waitpid(WNOHANG)` poll (10 ms → 5 s). The poll exists because, under parallel load, a child that exited
  before kqueue armed was occasionally never reported (observed in about 1 in 3 full-suite runs before the fix,
  0 in 10+ runs after).
- **Terminate.** Sends `killpg(SIGHUP)` to the session group and to the terminal's foreground group (jobs of an
  interactive shell), then `SIGKILL` to the same groups after 2 s regardless. This covers group members that ignore
  SIGHUP (tested).
- **Idle.** The helper is idle when no session is running and no client is connected. After a 10 s grace (env
  `MERCURY_PTYHOST_IDLE_GRACE`) it exits. `shutdownIfIdle` exits immediately when nothing is running.
  Exited-unattached sessions are reaped after 24 h (`MERCURY_PTYHOST_RETENTION_HOURS`).
- **Persistence.** `<dataRoot>/pty-host/sessions/<id>.json` (dir 0700) holds `PTYSessionInfo` plus `endedAt`. It never
  stores the environment or arguments. Records left by an earlier helper load as not running with an unknown status.
- **Security.** When the helper is team-signed, `main.swift` sets
  `listener.setConnectionCodeSigningRequirement(identifier "com.tekmium.mercury" and anchor apple generic and
  certificate leaf[subject.OU] = <own team>)`. Ad-hoc dev builds skip it and rely on the per-user launchd domain.
- **Client.** `PTYHostClient` hops every XPC callback to the main queue with `DispatchQueue.main.async`, which is FIFO
  and so preserves order. Concurrent handshakes are coalesced. Every request has a 10 s timeout plus an error-handler
  race guarded by a resume-once box. On a version mismatch it sends `shutdownIfIdle`, invalidates the connection and
  throws `.protocolMismatch`. On interruption or invalidation, attached engines re-attach over a fresh handshake
  without replaying the scrollback; sessions that are gone end with `onExit(nil)`. `register()` maps
  `.requiresApproval`, `kSMErrorLaunchDeniedByUser` and `.notFound` to typed errors.

### H1: terminate leaves background jobs running

`PTYSession.terminate` now targets every process of the terminal, not two process groups. Members are:
- processes whose **session id** is the leader's pid. Background jobs keep it even after the shell has exited.
- processes whose **controlling tty** is our slave, via `proc_listpids(PROC_TTY_ONLY, st_rdev)`, while the PTY is
  open.

Session id is needed, not just tty lookup (the review's suggestion, and what `PTYChannel` does). When the session leader
exits, the kernel dissociates the controlling terminal from the session, so tty lookup finds nothing once the shell is
gone. That includes the 2 s SIGKILL sweep, because the shell dies from the SIGHUP itself. I found this in a test
before relying on it.

The sequence:
1. SIGHUP, then SIGCONT, to each distinct pgid of the members (plus the leader while it is not reaped).
2. The PTY stays open; post-exit output is drained and dropped so writers cannot block.
3. After `killGrace` (2 s), SIGKILL by pid to every member still present.
4. Then the PTY is closed.

`terminate` also works after the shell exited on its own, so closing the tab still sweeps the jobs it left behind.
`HostedTerminalEngine.terminate()` now sends terminate for exited sessions too. Processes that left the session on
purpose (`setsid`, daemons) are out of reach by design.

New tests:
- `terminateKillsHangupIgnoringBackgroundJobsInTheirOwnGroups`: interactive `zsh -f -i` running `nohup /bin/sleep 100 &`
  and `(trap '' HUP; exec /bin/sleep 100) &`. It asserts that each job leads its own pgid (the case that escaped) and
  that both are gone after terminate.
- `terminateAfterLeaderExitKillsStragglers`: `set -m; nohup sleep 100 &` in a shell that exits by itself; a later
  terminate still kills the job.

### L2: SIGKILL to a possibly reused pgid

The delayed `killpg` on groups captured 2 s earlier is gone. The sweep re-enumerates members at kill time and kills by
pid only processes verified as ours at that moment (session id equals our leader's pid; the kernel does not hand out a
pid still in use as a session id). The leader is signalled by pid only while it is not yet reaped.

### M2: app memory unbounded under a flood

Implemented as the coordinator specified:
- **Protocol:** `PTYHostXPC.ack(_ sessionID:, bytes:)` added and `protocolVersion` bumped to 2. The existing mismatch
  handling covers old helpers.
- **Host send window:** a flow-controlled attachment (every XPC attachment) has a 2 MB window that refills only from
  acks. The send barrier is gone.
- **PTY read stall:** when the slowest flow-controlled attachment's backlog (sent and unacked, plus read and unsent)
  reaches the window, the session suspends its PTY read source. The kernel buffer fills and the child blocks. Reading
  resumes at half the window.
- **Scrollback:** stays authoritative; nothing is skipped (verified with 16 MB, twice the ring, byte-identical).
- **Engine credits:** `HostedTerminalEngine.outputConsumed(_:)` credits only stream bytes it handed to `onOutput`
  (scrollback replays are never counted). Bytes the engine drops are credited at once, and so are bytes returned from
  `attach(sessionID:)`.
- **Client batching:** `PTYHostClient.acknowledge` sends per session at ≥ 64 KB or after 16 ms. A consumer that never
  calls `outputConsumed` stalls the session, which is documented on the type.
- **Interactive echo:** unchanged. The window dwarfs an echo; typing round trip over XPC is 0.22 ms median.

**Ordering fix found while testing.** In about 1 of 6 runs, XPC handled an incoming `output` message before the
`attach` reply block on the client. Message-to-message order is FIFO, but a reply is not ordered against messages. My
original engine logic ("drop until the reply arrives") could therefore drop the first live bytes.

The host now opens every attachment's stream with an empty `output` message (stream-start marker), documented on
`attach`. The engine drops bytes before the marker (leftovers of an earlier attachment), buffers bytes after it until
`attach` returns, and is independent of when the reply lands. `attachReplyArrived` is removed.

Byte-identity tests run `stty -opost` first. With ONLCR, a writer blocked mid-`\r\n` on a full tty queue gets its `\r`
emitted twice by the kernel line discipline (`\r\r\n`). That is a terminal artifact flow control makes visible, not a
stream defect.

Measurements:

| Check | Result |
|---|---|
| Protocol test, app stops acking (`seq`, 16 MB) | host read paused at ~2.1 MB; app holds exactly 2,097,152 unacked bytes; after acks resume, all 16 MB arrive byte-identical |
| Engine flood, slow consumer (64 KB per 16 ms tick, models TerminalSession's budgeted feeder) | app queue peak 0.07–0.09 MB, footprint 8.3 → 19.7 MB |
| Engine flood, consumer stalled | host read paused at 6.2 MB, app queue exactly 2.00 MB, no further PTY reads |
| Engine flood, fast consumer, 20 MB `yes \| head -c` | completes, every byte exactly once, content verified byte for byte, footprint peak 32.3 MB (baseline 8.3 MB, includes the in-process host's 8 MB scrollback) |
| Engine flood, **500 MB** `yes \| head -c 500000000` (`FLOOD_BYTES=500000000`) | slow phase: queue peak 0.07 MB; stall: read paused at 7.0 MB, queue 2.00 MB; then all 500,000,000 bytes exactly once, content verified, in 210 s; footprint peak **31.8 MB** (baseline 6.9 MB), flat for the whole run |

Throughput is set by the kernel, not by this pipeline. `script -q /dev/null sh -c 'stty -opost; yes | head -c 50000000'`
alone runs at about 2.1 MB/s on this machine (23.7 s, almost all system time). The engine path reaches the same
~2.4 MB/s, so the 500 MB run is opt-in and the default test uses 20 MB.

### L3: timed-out attach leaks a helper attachment

`PTYHostClient.attach` now sends `detach` on every failure path (timeout, connection error, undecodable reply). It
does so only while the engine is still the registered one, so a newer attach is never cut off. Output that arrives for
a session with no live engine also triggers `detach`.

### Other notes for the coordinator

- The running agent `com.tekmium.mercury.ptyhost` (pid 71539, registered by the integrated app) is a protocol-1
  build. After rebuilding the app, the first handshake gets `.protocolMismatch(host: 1, client: 2)` and asks it to
  `shutdownIfIdle`. Until its sessions end, the app cannot attach to them. That is the designed update path, but
  expect it in local testing (or `launchctl kickstart -k` the agent once its sessions are disposable). I did not
  touch it, and I skipped my temporary-launchd re-check because it would collide with that registered Mach service.
- `TerminalSession` must call `outputConsumed` for every chunk it feeds from `onOutput`. Without that, a hosted session
  stalls after 2 MB. Other `onOutput` consumers of `HostedTerminalEngine` must do the same.
- Public API is unchanged except `HostedTerminalEngine.outputConsumed(_:)` (satisfies the new protocol requirement),
  `PTYHostClient.acknowledge(_:bytes:)`, `PTYSession.{acknowledge, attach(_:flowControlled:onSnapshot:), bytesRead,
  isReadPaused}`, and the `PTYOutputSink.deliver(output:sessionID:)` signature (completion removed).
